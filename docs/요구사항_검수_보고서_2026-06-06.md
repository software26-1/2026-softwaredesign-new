> **F6-3 판정 근거 (미충족 → 의도적 제외로 재분류, 2026-06-06)**
> 요구사항 명세서는 "상담 업데이트 시 알림"을 명시하나, 본 시스템은 상담 내역을 **학생·학부모에게 비공개하고 교사 간에만 공유**하는 정책으로 설계했다. 근거: `CounselingController`의 모든 엔드포인트가 `hasRole('TEACHER')`/`hasAnyRole('TEACHER','ADMIN')`로 STUDENT·PARENT 접근을 차단하고, `Counseling.isShared` 플래그는 학생/학부모 공개가 아니라 교사 간 공유 여부를 의미한다(`/shared` 엔드포인트도 교사 전용).
> 상담을 볼 권한이 없는 학생/학부모에게 "상담이 등록되었다"는 알림을 보내는 것은 비공개 정책과 모순되므로, 알림을 보내지 않는 것이 일관된 설계다. 따라서 이 항목은 기능 누락(미충족)이 아니라 **상담 비공개 정책에 따른 의식적 설계 결정**으로 분류한다. 상담의 민감성(학생 사생활·생활지도 내용)을 고려한 개인정보 보호 측면의 판단이기도 하다.

## 4. 보고서 기능 — 설계 대비 가장 크게 달라진 부분

설계(기능명세서 v2 row 15 + API 명세 v2 원문):

실제:

| 레이어 | 상태 |
|---|---|
| 백엔드 report 도메인 | 설계대로 존재 (`Report` 엔티티 file_path, `ReportService`, `ReportStorageService` S3/로컬 분기, OpenPDF/POI 의존성) — 단 `ReportGenerator`는 플레이스홀더 본문만 출력하는 **스텁** |

| 실제 사용 흐름 | `ReportPage.tsx`가 일반 조회 API들(analytics/record/counseling/feedback)로 데이터를 모아 **클라이언트에서 직접 생성**: PDF는 공문서 스타일 HTML + `window.print()`, Excel은 ExcelJS 5종 |

## 6. ERD vs 실제 DB 스키마

### 6-1. 테이블 수 변화

- 초기 ERD: 20개 테이블
- 최종: public 21개 + analytics 7개 = **28개**
- 계획 20개 전부 생성됨 (제거된 테이블 없음)

### 6-2. 추가된 테이블과 이유

| 테이블 | 마이그레이션 | 이유 |
|---|---|---|
| analytics.dim_student/dim_course/dim_date | V11 | 추가 요구사항(OLAP) — 스타 스키마 차원 테이블 |
| analytics.fact_student_course_term/fact_student_learning_summary/fact_class_course_stats | V11 | 학생x과목x학기 / 학생 종합 / 반x과목 집계 팩트 |
| analytics.etl_job_log | V11 | 배치 ETL 실행 이력 |
| device_token | V12 | FCM 푸시 — 사용자 1명 다기기(1:N), 토큰 영구 저장 필요 |

### 6-3. 주요 구조 변경 (V6 대규모 재정의)

V6가 11개 테이블을 DROP 후 API 명세 v2 기준으로 재생성 — 사실상의 "2차 ERD":
- enrollment: 교사-과목-학급 편성 → **학생-과목 수강 등록**으로 의미 변경 (교사 배정은 course.teacher_id로 흡수)
- curriculum: 학교 종속 → 전국 공통 교과(school_type 기준)
- report: teacher/student/title/content → requested_by/report_type/file_format/file_path 구조로 재설계
- class_group: 담임 컬럼 V6 제거 → V16 재추가 (담임 배정 기능 구현 시 필요해져 복귀)
- 이후 점진 변경: V17 전학 양교 이중 승인, V19 절대/상대평가 구분, V20 교사-교과 연결, V21 과목 학년 직접 저장

### 6-4. 중대 발견: JPA 엔티티와 Flyway 스키마 불일치

grade, grade_summary, counseling, feedback, student_record 5개 테이블에서 엔티티가 V6 스키마와 다르게 매핑돼 있다 (예: 엔티티는 `grade.student_id`·`grade_type`을 쓰지만 V6 스키마는 `exam_type`만 있고 student_id 없음; feedback은 `visible_to_*` vs DB `is_public_to_*`).

**의미: Flyway만으로 새 환경을 구축하면 해당 도메인이 런타임에 깨진다.** 현재 개발 DB는 과거 수동 보정 등으로 동작 중인 것으로 추정된다. 검수 중 이 불일치를 정렬하는 V22~V24 마이그레이션 + 엔티티 수정이 `fix/#110-schema-align` 브랜치에 준비돼 있다(미검증 — 데이터 삭제 마이그레이션 포함이므로 검토 후 채택 여부 결정 필요).

### 6-5. ERD 원본(컬럼 수준) vs 최종 스키마 전수 비교

원본: `docs/설계_ERD_원본.png` (erdCloud, 20개 테이블)

결론부터: **초기 ERD와 Flyway 최종 스키마는 대부분 일치한다.** V6 마이그레이션("align_schema_with_api_spec")이 바로 이 ERD에 맞추는 작업이었기 때문. grade(enrollment_id+exam_type), grade_summary(raw_score 등 9컬럼), feedback(category, is_public_to_*), counseling(counsel_date DATE, main_content), student_record(academic_year/semester/special_note), report(file_path "S3 파일경로" 라벨까지 ERD에 명시) 전부 ERD 그대로 DB에 구현됐다.

#### 완전 일치 (12개)

school, parent, admin, parent_student, curriculum, notification, grade, grade_summary, feedback, counseling, student_record, report — ERD 컬럼과 최종 스키마 동일 (이후 공통 추가된 is_deleted 제외)

#### ERD와 다르게 구현된 부분 (구조 변경)

| 테이블 | ERD 설계 | 실제 최종 | 변경 이유 |
|---|---|---|---|
| user | `login_id VARCHAR(50)`, `password_hash VARCHAR(255)`, name, role | `email`, `google_id`(nullable), `password`(관리자용), name, phone, role, `status`, school_name, `resident_number`(AES 암호화) | **인증 방식 전면 변경**: ID/PW 로그인 → Google OAuth2 + 관리자만 ID/PW. 가입 승인 플로우(status), 주민번호 암호화 필드 추가 |
| approval_request | 이중 승인자 모델: `approver_id1/2`, `approval1/2 VARCHAR(20)`, `processed_at1/2` | 단일 `approver_id` + `status` + V17의 `from_school_id/to_school_id`, `from_school_status/to_school_status` | 이중 승인 의도(전학 시 양교 승인)는 유지하되, 승인자 2명 컬럼 대신 학교 양측 상태 컬럼으로 재설계 |
| teacher | `class_group_id` (교사→학급 방향) | `position`(HOMEROOM/SUBJECT/NON_SUBJECT) + class_group.`homeroom_teacher_id`(V16, 학급→교사 역방향) + `curriculum_id`(V20) | 담임 연결 방향을 역전(학급이 담임을 가리킴). 직책 구분과 담당 교과 연결 추가 |
| enrollment | `enrolled_at TIMESTAMP` 포함 | V9에서 `enrolled_at` 삭제 (created_at으로 대체) | 중복 정보 제거 |
| attendance | `attend_date DATE`, reason VARCHAR(255) | `date DATE`, reason TEXT | 컬럼명 단순화, 사유 길이 제한 해제 |
| course | course_type enum 등 ERD와 일치 | + `evaluation_type`(V19 절대/상대평가), `grade`(V21), teacher_id nullable(V21) | 중·고교 평가 방식 분기, 학년 직접 저장 등 기능 확장 |
| student | user_id/school_id/class_group_id/student_number | 동일 (V3의 birth_date는 V7에서 삭제 — ERD에 없던 컬럼을 정리) | 일치로 수렴 |

#### ERD에 없는데 추가된 것

device_token(V12, FCM), analytics 스키마 7개 테이블(V11, OLAP) — 6-2 참조. 그 외 전 테이블 공통 `is_deleted`(소프트 삭제, V7/V10/V14/V15).

#### 6-4 불일치의 재해석

ERD 원본 확인으로 6-4의 결론이 명확해졌다: **DB 스키마는 ERD를 충실히 따랐고, ERD에서 이탈한 쪽은 JPA 엔티티다** (grade/grade_summary/feedback/counseling/student_record 5개). 즉 엔티티 구현 시점에 ERD가 아닌 다른 기준(아마 초기 V3 구조 또는 자체 판단)으로 작성된 것. 정합 방향을 정할 때 "ERD·DB가 설계 원본"이라는 점을 고려해야 한다 — 단, 현재 서비스 코드 전체가 엔티티 기준으로 동작하므로 `fix/#110-schema-align`처럼 DB를 엔티티에 맞추는 방향이 현실적이다.

## 7. RDD 도메인모델 vs 코드 도메인

## 8. 검토 부문 체크리스트 (7개)

1. **요구사항 미충족 3건 — 처리 완료 (2026-06-06)**. 상담 알림(F6-3)은 상담 비공개 정책에 따른 의도적 제외로 재분류, 정기 백업(N4-1)·장애 복구(N4-2)는 구현 완료. 상세는 9절.
2. **변경구현 — 보고서(E2)·실시간(N3-2)** — 서버 생성+S3 설계 → 클라이언트 생성으로 바꾼 이유를 발표 자료에 명시. 미사용 백엔드 report 파이프라인과 `reportService.ts`는 정리 또는 활성화 중 택일. 실시간 알림은 폴링이라도 추가할지 결정.
3. **아키텍처 괴리 — 입장 정리 완료 (11절)**. S3는 백업 용도로 재활용(해소), SES/FCM은 발송 로직 완성·스위치 off(선택 활성화 설계), Kafka는 가점 대응 구현 완료, EC2 2대 분리는 인프라 담당(팀원) 영역으로 표기.
4. **ERD 괴리 — 입장 정리 완료 (12절)**. 20개 테이블 컬럼 전수 비교 결과 12개 완전 일치, 구조 변경 3개(user 인증, approval_request, teacher 방향)뿐 + 소소한 2개. 모두 의도적 개선이며 사유를 본 보고서에 문서화(노션 별도 반영은 보류).
5. **엔티티-스키마 내부 불일치 — 해결 완료 (14절)**. grade 등 5개 도메인을 V23 마이그레이션으로 정합(데이터 보존 RENAME 방식). 일회용 PostgreSQL에 V1~V23 적용 + 5개 테이블 실제 INSERT/SELECT 검증 통과. 자바 코드 변경 0.
6. **기능명세 기타** — 학생부 담임 제한·학생당 1 row(학기별 이력 불가), 성적 총점/문자등급 자동계산 누락, 과목별 필터 API 부재, 암호화 범위(주민번호만), 챗봇은 기획 문서 외 구현(Claude → Gemini).
7. **`fix/#110-schema-align` 브랜치 대신 신규 작성으로 해결 (14절)**. 미검토 fix 브랜치는 컬럼 DROP·행 DELETE를 포함해 채택하지 않고, 데이터 보존(RENAME+ADD+NOT NULL해제) 방식의 V23을 새로 작성·검증했다. fix 브랜치는 폐기 가능(런타임 버그 수정분만 별도 검토 시 재활용).

## 9. 1번 부문 조치 내역 (2026-06-06)

검수 후속 체크리스트 1번(요구사항 미충족 3건)을 처리한 기록이다. 발표 자료에 그대로 활용 가능하도록 "왜 그렇게 결정했는가 → 어떻게 구현했는가 → 어떻게 동작하는가" 순으로 정리한다.

### 9-1. 상담 알림(F6-3) — 비공개 정책에 따른 의도적 제외

**왜 이렇게 결정했나**
- 상담 내역은 학생 사생활·생활지도 내용을 담는 민감 정보다. 본 시스템은 상담을 **학생·학부모에게 비공개하고 교사 간에만 공유**하는 정책으로 설계했다.
- 근거(코드): `CounselingController`의 전 엔드포인트가 `hasRole('TEACHER')`/`hasAnyRole('TEACHER','ADMIN')`로 STUDENT·PARENT 접근 차단. `Counseling.isShared`는 학생/학부모 공개가 아니라 교사 간 공유 토글이며 `/shared`도 교사 전용.
- 볼 권한이 없는 학생/학부모에게 "상담이 등록되었다"고 알리는 것은 비공개 정책과 모순이다. 따라서 알림을 보내지 않는 것이 일관된 설계다.

**결론**: 요구사항 명세서의 "상담 업데이트 시 알림"은 학생/학부모 대상 알림을 전제하나, 본 시스템의 상담 비공개 정책상 이를 의도적으로 제외한다. 기능 누락이 아니라 **개인정보 보호 관점의 설계 결정**이다. 코드 변경 없음.

### 9-2. 정기 백업(N4-1)

**왜 이렇게 결정했나 (방향 선택)**
- 운영이 EC2 1대에 PostgreSQL 컨테이너로 올라가 있어 **서버가 죽으면 데이터도 같이 죽는** 단일 장애점이다. docker volume은 영속성일 뿐 백업이 아니다.
- 따라서 백업본을 EC2 바깥(S3)에 두는 것을 핵심 조건으로 삼았다. 마침 아키텍처 다이어그램에 Amazon S3가 있고 AWS SDK가 이미 의존성에 있어, **추가 인프라 없이 S3를 백업 보존 용도로 실제 활용**하는 방향을 택했다(다이어그램의 S3 미사용 지적도 일부 해소).
- pg_dump는 custom format(`-Fc`)을 사용 — `pg_restore`로 선택/병렬 복원이 가능하고 plain SQL보다 유연하다.

**어떻게 구현했나**: `scripts/db-backup.sh`
```
1) docker exec school_postgres pg_dump -U postgres -Fc school_mgmt | gzip
   → ./backups/school_mgmt_YYYYMMDD_HHMMSS.dump.gz
2) BACKUP_S3_BUCKET 설정 시 → aws s3 cp 로 s3://<버킷>/db-backups/ 업로드
   (aws CLI 없거나 실패해도 로컬 백업은 보존 — WARN 후 계속)
3) RETENTION_DAYS(기본 7일) 초과 로컬 백업 자동 삭제
```

**어떻게 동작하나**
- 수동: `./scripts/db-backup.sh`
- 정기: EC2 crontab에 `0 4 * * *`(새벽 4시, ETL 3시 이후) 등록 — `docs/DISASTER-RECOVERY.md` 1-4
- S3는 옵션이다. 자격증명 없이도 로컬 백업이 동작하고, 운영에서 `BACKUP_S3_BUCKET` 한 줄만 주면 오프사이트 백업으로 승격된다.
- 환경변수: `BACKUP_S3_BUCKET`, `RETENTION_DAYS`, `AWS_REGION` 등 (`backend/.env.example`에 등록).

### 9-3. 장애 복구(N4-2)

**왜 이렇게 결정했나**: 장애를 세 유형으로 나눠 대응한다. 자동 복구(컨테이너), 데이터 복원(스크립트), 전체 재구축(S3 백업)으로 계층화하면 대부분의 실패 시나리오를 커버한다.

**어떻게 구현했나**
1. **자동 재기동**: `docker-compose.yml` 전 6개 서비스에 `restart: unless-stopped` + postgres/redis `healthcheck` 추가. 컨테이너 비정상 종료·EC2 재부팅 시 Docker가 자동 복귀.
2. **복원 스크립트**: `scripts/db-restore.sh`
   - 인자 없으면 최신 로컬 백업 자동 선택, `s3://...` 인자면 먼저 다운로드
   - **복원 전 현재 DB를 자동 백업**(`pre_restore_*.dump.gz`) — 복원이 잘못돼도 직전 상태로 롤백 가능
   - `yes` 대화형 확인(자동화 시 `FORCE=1`) 후 `pg_restore --clean --if-exists`로 교체 복원
3. **복구 절차 문서**: `docs/DISASTER-RECOVERY.md` — 시나리오 A(컨테이너 장애)/B(데이터 손상·마이그레이션 사고)/C(EC2 전체 소실)별 명령어, RPO/RTO, 점검 체크리스트.

**어떻게 동작하나 (시나리오별)**
- A. 컨테이너 죽음 → `restart: unless-stopped`로 자동 복구 (수동: `docker compose up -d`)
- B. 데이터 손상 → `./scripts/db-restore.sh [백업파일]` (위험한 마이그레이션 전 `db-backup.sh` 선행 권장 — 7번 fix 브랜치 적용 시 특히)
- C. EC2 소실 → 새 인스턴스에서 클론 + `.env` 복원 → `docker compose up -d postgres redis` → `db-restore.sh s3://...` → `docker compose up -d`

**산출물 목록**
- `scripts/db-backup.sh`, `scripts/db-restore.sh` (실행 권한 부여, bash 문법 검증 통과)
- `docker-compose.yml` (restart 정책 + healthcheck, `docker compose config` 검증 통과)
- `docs/DISASTER-RECOVERY.md` (운영 가이드)
- `.gitignore`(backups/ 제외), `backend/.env.example`(백업 환경변수 문서화)

## 10. 2번 부문 조치 내역 (2026-06-06)

검수 후속 체크리스트 2번(보고서 변경구현 + dead code + 실시간 N3-2)을 처리한 기록이다.

### 10-1. 보고서 서버/S3 저장 폐기 — 설계 판단

**왜 이렇게 결정했나**
- 보고서는 "지금 이 시점 데이터의 스냅샷"이다. 사용자가 버튼을 누르면 브라우저가 즉석에서 생성해 본인 PC로 바로 내려받는다(PDF: `window.print()`, Excel: ExcelJS).
- 이 구조에서 서버/S3에 추가로 저장하는 것은 다음 이유로 불필요하고 오히려 해롭다:
  1. 동일 파일이 서버에도 중복 적재 → 스토리지 낭비
  2. 데이터는 계속 변하는데 저장된 보고서 파일은 과거 값으로 고정 → 최신 데이터와 불일치, 혼란 유발
  3. 성적·상담 등 민감정보가 담긴 파일을 서버/S3에 쌓아두면 보안·개인정보 관리 부담만 증가
- 따라서 설계상의 "서버 생성 + S3 저장 + 서버 다운로드"는 폐기하고, "클라이언트 생성 + 사용자 로컬 저장"으로 일원화한다. 이는 요구사항 미달이 아니라 **구현 과정에서 더 합리적인 방향을 채택한 개선**이다.

**S3의 새 역할**: 보고서 저장 용도였던 S3는 N4(백업)에서 **DB 백업 보존소**로 재활용했다(9-2절). 아키텍처 다이어그램의 S3가 실제로 쓰이게 되어 "S3 미사용" 지적도 해소됐다.

### 10-2. dead code 처리

서버 보고서 생성/저장 라인이 어느 화면에서도 호출되지 않는 죽은 코드임을 확인하고(프론트 `reportService.ts`를 import하는 파일 0개, 백엔드 report 도메인 외부 참조·테스트 0개) 다음과 같이 정리했다:

| 대상 | 조치 |
|---|---|
| `frontend/src/services/reportService.ts` | 구현 전체 주석 처리 + 사유 헤더 주석. `export {}`로 모듈 유지(타입체크 통과 확인) |
| `backend/.../report/controller/ReportController.java` | 클래스 상단에 "미사용 안내" Javadoc 주석 — 실제 흐름에서 호출 안 됨, S3 저장 폐기 사유 명시 |
| 백엔드 report 도메인(Service/Generator/StorageService) | 컴파일 유지(Spring 빈 부분 주석은 더 지저분해지므로). 사유는 컨트롤러 주석에 집약. 향후 일괄 제거 후보로 표기 |

> 삭제가 아니라 주석 처리를 택한 이유: 이력 보존 + 발표 시 "원래 서버 생성 설계였으나 이런 이유로 클라이언트 생성으로 전환" 설명 근거를 코드에 남기기 위함.

### 10-3. N3-2 준실시간 알림 — 폴링 구현

**왜 폴링(A)인가**
- 요구사항의 "실시간 업데이트"를 만족하는 방법은 WebSocket/SSE(서버 푸시), 폴링(주기 조회), 현행(페이지 진입 시 1회)으로 나뉜다.
- 본 시스템은 교육용으로 초 단위 즉시성이 필수는 아니며, WebSocket/SSE는 인프라·서버 부담이 크다. 30초 폴링이면 사용자 체감상 충분히 "자동 갱신"되면서 구현이 가볍다. 따라서 폴링을 채택했다.

**어떻게 구현했나**

| 위치 | 구현 |
|---|---|
| `frontend/src/components/layout/Header.tsx` | 알림 배지(`fetchUnread`)를 `setInterval` 30초 주기로 호출. 헤더는 전 페이지에 상주하므로 어느 화면에서든 배지가 자동 갱신됨 |
| `frontend/src/pages/NotificationPage.tsx` | 알림 목록(`load`)을 30초 주기 폴링 — 페이지를 열어둔 채로도 새 알림이 자동 반영 |

공통 최적화:
- **탭 가시성 연동**: `visibilitychange` 이벤트로 탭이 백그라운드(숨김)면 폴링을 멈춰 불필요한 요청을 차단하고, 다시 화면으로 돌아오면 즉시 1회 갱신 후 폴링을 재개한다.
- **정리(cleanup)**: 컴포넌트 언마운트 시 `clearInterval` + 이벤트 리스너 해제로 누수 방지.
- 기존 `notification-updated` 커스텀 이벤트(읽음 처리 등 사용자 액션 직후 즉시 갱신)와 병행 — 액션 기반 즉시 갱신 + 시간 기반 폴링의 이중 트리거.

**어떻게 동작하나**
- 사용자가 로그인해 어느 화면이든 보고 있으면, 30초마다 헤더의 안읽음 배지가 서버 최신 상태로 갱신된다.
- 알림 페이지를 열어두면 목록도 30초마다 새 알림으로 채워진다.
- 다른 탭으로 이동하면 폴링이 멈춰 서버 부하·네트워크를 아끼고, 돌아오면 즉시 최신화된다.
- 별도로 FCM 모바일 푸시(`PushNotificationSender`, 기본 비활성)는 앱/브라우저를 안 보고 있을 때의 OS 알림용으로 보완 관계다 — 폴링(웹 화면 내 갱신)과는 다른 계층.

**검증**: 프론트엔드 `tsc --noEmit` 타입체크 통과(exit 0).

**산출물**: `Header.tsx`, `NotificationPage.tsx`(폴링), `reportService.ts`(주석 처리), `ReportController.java`(사유 주석).

## 11. 3번 부문 — 아키텍처 괴리 입장 정리 (2026-06-06)

다이어그램(v3.1)과 실제 구현의 차이를 항목별로 어떻게 설명할지 정리한다.

### 11-1. Amazon S3 — 용도 변경 (해소)

보고서 저장용으로 설계됐으나, 보고서는 클라이언트 생성+로컬 저장이라 서버/S3 저장이 불필요(10-1절). S3는 **DB 백업 보존소**로 재활용했다(`scripts/db-backup.sh`, 9-2절). 다이어그램의 S3가 실제로 동작하게 되어 미사용 문제 해소.

### 11-2. AWS SES(이메일) · Firebase FCM(푸시) — 발송 로직 완성, 자격증명(키) 미연결

> 요점: 이메일/푸시는 **화면 알림(폴링 포함) 위에 얹는 선택적 부가 채널**이다. 요구사항의 "학부모·학생 자동 알림"은 화면 알림으로 이미 충족되므로, 이메일/푸시는 활성화하지 않아도 요구사항 미달이 아니다. 발송 로직은 완성돼 있고 외부 자격증명(키)만 연결하면 동작한다.

**현황(코드 확인)**: 발송 로직이 실제로 완성돼 있고 화면 알림과 동일 경로로 배선돼 있다.
```
성적/피드백 입력 → NotificationService.notify() → 알림 DB 저장
                                              → NotificationDispatcher.dispatch()
                                                  ├─ EmailNotificationSender.send()   (SES v2 실제 sendEmail 호출)
                                                  └─ PushNotificationSender.sendToTokens()  (FCM 실제 멀티캐스트)
```
즉 화면 알림이 생길 때마다 같은 내용을 이메일·푸시로도 동시에 발송하도록 구현돼 있다. 다만 `app.notification.email.enabled` / `app.notification.push.enabled`가 기본 `false`라 현재는 로그만 남기고 실제 발송은 하지 않는다.

**입장(구현 완료, 키 미연결)**: 발송 로직은 완성됐으나 외부 자격증명을 받지 않아 비활성이다.
- 이메일(SES): AWS 계정 + 인증된 발신 주소(verified sender) + 샌드박스 해제가 필요. 별도 AWS 세팅이라 받지 않음.
- 푸시(FCM): Firebase 인증키 + **프론트엔드의 기기 토큰 등록 코드**가 추가로 필요. 현재 프론트에 firebase 패키지·토큰 발급/등록 로직이 없어, 백엔드 스위치만 켜도 보낼 대상(device_token)이 없다. 즉 푸시는 키 연결 + 프론트 작업이 남았다.

요구사항은 화면 알림으로 충족되므로 이 채널들의 비활성은 미달이 아니다. 발표 시 "외부 발송 채널은 로직까지 구현 완료, 자격증명·프론트 토큰 등록만 연결하면 동작"으로 설명한다.

### 11-3. Kafka — 가점 대응, 기본 활성화 (2026-06-06)

추가 요구사항의 "데이터 변경 이벤트 기반 분석 DB 갱신(Kafka 등 메시지 스트림) 가점"에 대응해 구현했다. `AnalyticsEventBridge`(발행) → Kafka 토픽(`grade/attendance/feedback.changed`) → `AnalyticsKafkaConsumer`(수신) → 증분 분석 갱신 파이프라인 완성.

**2026-06-06 기본 활성화**: Kafka 브로커는 docker-compose의 `kafka` 컨테이너로 전체 스택과 함께 기동되므로 별도 자격증명·외부 의존성이 없다. 따라서 기본값을 활성으로 전환했다(`application.yml` `app.kafka.enabled: ${KAFKA_ENABLED:true}`, `.env.example` `KAFKA_ENABLED=true`). 브로커 없이 단독 실행할 때만 `KAFKA_ENABLED=false`로 끄면 Spring 동기 이벤트 폴백으로 동작하는 이중 구조라 안전하다. 다이어그램에는 없던(설계 이후 추가된) 가점 요소를 실제로 켜서 운영·시연한다.

### 11-4. EC2 구성 — 인프라 담당(팀원) 영역

다이어그램은 앱 EC2 + DB 전용 EC2의 2대 분리 구성이다. 현재는 단일 EC2에 컨테이너로 통합돼 있으나, 이는 **인프라 담당(팀원)의 영역**이며 다이어그램대로 EC2 2대 분리 구성으로 가는 것을 목표로 한다. 본 검수는 코드/애플리케이션 범위를 다루며, EC2 분리·배포 토폴로지는 인프라 담당자가 처리한다.

### 11-5. 기타(다이어그램에 없던 추가분)

Nginx(리버스 프록시·TLS), Prometheus+Grafana(모니터링), GHCR(컨테이너 레지스트리)는 다이어그램에 없었으나 운영 편의를 위해 추가됐다. 모두 긍정적 보강이다.

## 12. 4번 부문 — ERD 괴리 입장 정리 (2026-06-06)

ERD 원본(`docs/설계_ERD_원본.png`) 20개 테이블을 **컬럼 단위로 전수 비교**한 결과다(Flyway V1~V21 대조). 결론: **거의 바뀌지 않았다.** V6 마이그레이션이 ERD에 맞추는 작업이었기에 DB가 ERD를 충실히 따랐다.

### 12-1. 비교 요약

| 구분 | 테이블 수 | 목록 |
|---|---|---|
| 컬럼까지 완전 일치 | 12 | school, parent, admin, parent_student, curriculum, notification, grade, grade_summary, feedback, counseling, student_record, report |
| 구조 의도 변경 | 3 | user, approval_request, teacher↔class_group |
| 소소한 변경 | 2 | enrollment(enrolled_at 삭제), attendance(attend_date→date) |
| 공통 추가 | 전체 | is_deleted(소프트 삭제), analytics 스키마 7개·device_token(설계 이후 추가) |

### 12-2. 구조 변경 3건의 사유

| 변경 | ERD 설계 | 실제 | 변경 사유 |
|---|---|---|---|
| user 인증 | `login_id` + `password_hash` (자체 로그인) | `email`/`google_id` + 관리자만 `password` + `status`(가입승인) + `resident_number`(AES) | 자체 회원가입·비밀번호 관리의 보안 부담을 줄이고 Google OAuth로 전환. 비번 분실 대응·해시 관리가 불필요해짐 |
| approval_request | 승인자 2명 컬럼(approver_id1/2, approval1/2, processed_at1/2) | 단일 approver + 양교 상태(from/to_school_id, from/to_school_status, V17) | 전학 승인을 "승인자 2명"이 아니라 "보내는 학교/받는 학교 양쪽 상태"로 모델링하는 것이 실제 전학 프로세스에 더 정확 |
| teacher↔class_group | teacher가 `class_group_id` 보유 | class_group이 `homeroom_teacher_id` 보유(V16) + teacher에 `position`·`curriculum_id` | 한 반의 담임은 1명이고 교사는 여러 반에 관여하므로, "반이 담임을 가리키는" 방향이 정규화상 자연스러움 |

모두 ERD가 틀렸다기보다 **구현하며 더 정확·안전한 방향으로 의도적으로 개선**한 것이다. (노션 ERD 문서에 별도 변경 이력 반영은 보류 — 본 보고서로 사유 문서화를 갈음)

### 12-3. 진짜 손볼 불일치는 따로 (5·7번)

ERD/DB는 정합하나 **JPA 엔티티 5개(grade, grade_summary, counseling, feedback, student_record)가 ERD/DB를 따라가지 않은** 불일치가 별도로 존재한다(6-4·6-5절). 이는 의도적 설계 변경(4번)과 성격이 다른 "정합성 버그"로, 5번(위험 인지)·7번(fix 브랜치 검증)에서 다룬다.

### 13-2. 암호화 범위 (N2-1) — 현 상태 유지 + 설계 설명

명세서는 "개인정보·성적 암호화"라고만 적혀 있고 구체적 필드 지정은 없다. 현재 주민등록번호만 AES-256 암호화(`AesEncryptionConverter`), 성적은 평문이다.

**성적을 암호화하지 않는 이유(설계 판단)**: 성적은 평균·석차·내신등급(백분위) 계산의 대상이고, 이 계산은 DB/ETL의 SQL(`PARTITION BY`, percentile)에서 수행된다. 성적을 암호화하면 DB가 암호문에 대해 집계·정렬을 할 수 없어, 전 성적을 앱으로 꺼내 복호화 후 계산해야 하므로 OLAP/ETL 분석 아키텍처가 무너진다. 따라서 성적은 암호화 대신 **역할 기반 접근제어**(`@PreAuthorize` + 학교 격리 + 본인/자녀 검증)로 보호한다. 법정 민감정보(주민번호)만 암호화하는 것은 업계 표준 관행이다.

### 13-3. 부하테스트 대비 (N3-1: 다수 교사 동시 접속)

명세서 비기능 N3은 "다수 교사 동시 접속"과 "실시간 업데이트"를 포함하며, 교수의 부하테스트로 검증될 항목이다. 검수 시 두 가지 약점을 발견하고 보강했다.

**약점 1 — 운영 테이블 인덱스 부재**
- PostgreSQL은 PK에는 인덱스를 자동 생성하나 FK에는 만들지 않는다. 운영 테이블(grade, feedback, counseling, attendance, enrollment, notification, student, student_record 등)은 `student_id` 등으로 조회가 빈번한데 인덱스가 없어 매 조회가 풀 테이블 스캔이었다. 데이터가 쌓이고 동시 요청이 늘면 급격히 느려진다.
- **조치**: `V22__add_operational_indexes.sql` — 자주 조회되는 FK·필터 컬럼에 인덱스 20개 추가(소프트삭제 테이블은 `(fk, is_deleted)` 복합 인덱스). `IF NOT EXISTS`로 멱등.
- **검증**: 일회용 PostgreSQL 16 컨테이너에 V1~V22 전체 순차 적용 → 전부 성공. `EXPLAIN`으로 조회가 실제 인덱스를 타는 것 확인(`Seq Scan` → `Bitmap Index Scan on idx_feedback_student`). 인덱스는 데이터·기능을 변경하지 않고 조회 속도만 개선하므로 기능 안전.

**약점 2 — 커넥션 풀 기본값**
- HikariCP 풀 튜닝이 없어 기본 최대 10개. 교사 수십 명 동시 접속 시 커넥션 부족으로 대기·타임아웃 우려.
- **조치**: `application.yml` `spring.datasource.hikari` — `maximum-pool-size: 30`(기본), `minimum-idle: 10`, `connection-timeout: 30s`, `max-lifetime: 30m`. 환경변수(`DB_POOL_MAX/MIN`)로 운영 조정 가능. PostgreSQL 기본 `max_connections`(100) 내 안전 범위.

**부하테스트 지금 가능 여부**: 위 보강으로 애플리케이션·DB 레벨 준비는 완료. 실제 부하테스트(JMeter/k6/Gatling 등으로 동시 사용자 시뮬레이션)는 배포 환경(EC2)에서 인프라 담당과 함께 수행한다. Prometheus+Grafana로 부하 중 지표(응답시간, 커넥션 사용량, CPU) 모니터링 가능.

### 13-4. 마이그레이션 번호 안내

V22는 부하 대비 인덱스다. 5·7번(엔티티-스키마 정합) 작업의 마이그레이션은 V23 이후로 이 뒤에 배치한다. (`fix/#110-schema-align` 브랜치의 기존 V22~V24는 미검토 상태이며, 채택 시 V23+로 재번호.)

## 14. 5·7번 부문 — 엔티티-스키마 정합 (2026-06-06)

### 14-1. 문제 (재확인)

`ddl-auto: none`이라 Flyway가 만든 스키마가 그대로 사용된다. 그런데 V6 마이그레이션이 일부 테이블을 API 명세 기준으로 재정의하면서, 이후 작성된 JPA 엔티티가 기대하는 컬럼명과 어긋났다. 5개 테이블에서 확인:

| 테이블 | 엔티티 기대 컬럼 | V6 스키마 실제 | INSERT 여부 |
|---|---|---|---|
| grade | student_id, grade_type, score(nullable) | (student_id 없음), exam_type, score NOT NULL | save() 호출됨 → 깨짐 |
| feedback | visible_to_student/parent, type | is_public_to_student/parent, category | save() 호출됨 → 깨짐 |
| counseling | counseled_at(TIMESTAMP), content | counsel_date(DATE), main_content | save() 호출됨 → 깨짐 |
| student_record | achievements, volunteer_hours, career_aspirations | special_note만(나머지 없음) | save() 호출됨 → 깨짐 |
| grade_summary | student_id, class_group_id, year, semester, average_score | enrollment_id 기준 V6 구조 | 조회 시 깨짐 |

결과: 깨끗한 DB에 Flyway만으로 기동하면 성적·피드백·상담·학생부 도메인이 런타임 실패. (현 dev DB는 과거 수동 보정으로 동작)

### 14-2. 해결 방식 — 데이터 보존, 자바 변경 없음

미검토 `fix/#110-schema-align` 브랜치(컬럼 DROP·행 DELETE 포함)를 채택하지 않고, **데이터 보존 방식**으로 `V23__align_schema_with_entities.sql`을 새로 작성했다.

- **RENAME**(데이터 보존): exam_type→grade_type, is_public_to_*→visible_to_*, category→type, counsel_date→counseled_at(DATE→TIMESTAMP), main_content→content, special_note→achievements
- **ADD + 백필**: grade.student_id(enrollment 경유), grade_summary.{student_id,year,semester,average_score}(enrollment→course 경유), student_record.{volunteer_hours,career_aspirations}
- **NOT NULL 해제**(DROP 대신): score, grade_summary의 V6 레거시 컬럼(enrollment_id,raw_score 등) — 엔티티가 채우지 않으므로 향후 INSERT 안전
- **멱등성**: 모든 RENAME을 `information_schema` 존재 확인 DO 블록으로 감싸, 이미 보정된 dev DB에 적용해도 no-op(안전)
- **자바 코드 변경 0**: 엔티티들이 모두 camelCase→snake_case 기본 명명을 기대하므로 DB만 맞추면 동작

데이터 삭제(DROP/DELETE)는 전혀 없다.

### 14-3. 검증 (실제 DB 테스트)

1. 일회용 PostgreSQL 16 컨테이너에 **V1~V23 전체 순차 적용 → 전부 성공**
2. 5개 테이블의 엔티티 기대 컬럼이 모두 존재함을 `information_schema`로 확인
3. **엔티티 모양 그대로 5개 테이블에 실제 INSERT → 전부 성공**(NOT NULL 충돌 없음)
4. 새 컬럼명(grade_type, visible_to_student, counseled_at, achievements, volunteer_hours, average_score)으로 **SELECT → 5건 모두 정상 조회**
5. 백엔드 `compileJava` 통과(exit 0)

### 14-4. 남은 enhancement (별도)

- **학생부 학기별 이력(F2-3)**: 스키마는 정합됐으나(academic_year/semester 존재), 엔티티가 `@OneToOne(unique)`이고 서비스가 학생 단위 upsert라 학생당 1 row만 유지된다. 학기별 이력 누적을 원하면 `@OneToOne`→`@ManyToOne` 전환 + Repository(findByStudentIdAndAcademicYearAndSemester) + 서비스 upsert 로직 변경이 필요하다. 이는 런타임 파손이 아니라 기능 한계이므로 별도 enhancement로 분리한다.

- V23: 엔티티-스키마 정합(본 절)
